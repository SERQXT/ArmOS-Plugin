# Skill: AppStudio / Image Component

## Overview

The Image component displays a static uploaded image file inside an AppStudio app.
It is **not** a rooster card — there is no DML, no params, no data binding, and no
dataset subscription. The image is uploaded once and rendered directly from the Domo
file storage system.

Card type: `"document"`

This is the simplest AppStudio component to create programmatically — two API calls
(upload + create card) before the standard app creation flow.

---

## How It Works

```
1. Upload image file  →  POST /api/data/v1/data-files (multipart)
                         → { dataFileId }

2. Create card        →  POST /api/content/v1/cards
                         type: "document", documentId: "{dataFileId}:undefined"
                         → { cardId, metadata.revisionId }

3. (optional) Poll    →  GET /api/content/v1/doc-previews/{cardId}/{revisionId}/meta
                         → 404 while processing, 200 when ready

4. Build app          →  Standard 11-step app creation flow
```

---

## Step 1 — Upload Image File

```
POST /api/data/v1/data-files
Content-Type: multipart/form-data  ← set automatically by fetch/browser, do NOT set manually
Accept: application/json
Cookie: <session>
```

Body: `FormData` with a single field:

```
file = <binary image data>  (filename and MIME type attached to the blob)
```

**Important:** Do NOT set `Content-Type` manually on this request. The multipart
boundary is generated by the FormData/fetch layer. Setting it manually will break
the upload.

**Response:**

```json
{ "dataFileId": 61 }
```

Timing: ~2.8 seconds (image upload + server-side processing starts).

---

## Step 2 — Create Card

```
POST /api/content/v1/cards
Content-Type: application/json;charset=UTF-8
X-Requested-With: XMLHttpRequest
```

**Body:**

```json
{
  "type": "document",
  "description": "<filename>",
  "metadata": {
    "title": "<filename>",
    "documentId": "<dataFileId>:undefined",
    "usingSampleData": "",
    "kpiType": "document",
    "description": "<filename>"
  }
}
```

| Field | Notes |
|---|---|
| `type` | Always `"document"` — this is NOT a `"rooster"` card |
| `documentId` | `"{dataFileId}:undefined"` — literally the string "undefined" as a revision placeholder |
| `kpiType` | `"document"` — required |
| `description` | The filename (e.g., `"logo.png"`) — appears in the card title |

**Response:**

```json
{
  "metadata": {
    "title": "logo.png",
    "documentId": "61:undefined",
    "revisionId": "62",
    "kpiType": "document"
  },
  "id": 683448557,
  "type": "document",
  "mimeType": "image/png",
  "title": "logo.png",
  ...
}
```

Capture `id` → `cardId` and `metadata.revisionId` → `revisionId` from this response.

> **`documentId: "{dataFileId}:undefined"`** — the "undefined" placeholder is correct.
> The server resolves the actual revision on its side. Do not attempt to insert the
> real revision ID here — it won't work and is not how the API expects it.

---

## Step 3 — Wait for Processing (optional poll)

The server asynchronously processes the uploaded image (generates previews). You can
poll for completion:

```
GET /api/content/v1/doc-previews/{cardId}/{revisionId}/meta
```

- Returns `404` while the image is being processed (~0–5 seconds)
- Returns `200` when the preview is ready

This step is optional for creating a valid app — the card will load eventually even
if you proceed without waiting. Only poll if you need to confirm the image is rendered
before proceeding.

To fetch the rendered PNG preview:

```
GET /api/content/v1/doc-previews/{cardId}/{revisionId}/PNG
```

Returns image bytes (binary). Timing: ~7 seconds (large image render).

---

## Step 4 — App Creation Flow (standard 11 steps)

The Image component uses the identical app creation sequence as Gallery, Banner, and
List components. Unlike rooster components, there is **no** `rooster/query` binding
step and no `PUT /api/content/v1/cards/<cardId>` update step.

**Simplified flow (9 steps for Image — no data binding):**

1. `POST /api/content/v1/dataapps` → `appId`, `landingViewId`, `layoutId`
2. `PUT /api/content/v1/dataapps/<appId>/persistSettings`
3. `PUT /api/content/v1/dataapps/<appId>`
4. `PUT /api/content/v1/dataapps/<appId>/navigation/reorder`
5. `PUT /api/content/v1/cards/bulk/pages` — assign card to page
6. `PUT /api/content/v4/pages/layouts/<layoutId>/writelock` — acquire lock
7. `PUT /api/content/v4/pages/layouts/<layoutId>` — set layout
8. `DELETE /api/content/v4/pages/layouts/<layoutId>/writelock` — release lock

> **Card is created before the app** (Steps 1–2 above happen before Step 4's app
> creation). The `cardId` from Step 2 is used directly in Step 8's `cards/bulk/pages`.

### POST /api/content/v1/dataapps body

Same as all other AppStudio components — see `skill-appstudio-gallery.md` or
`skill-appstudio-banner.md` for the full body. Include `owners`, `enabled`,
`showNavigation`, etc. to get `views[0].layout.layoutId` populated.

### DELETE card

```
DELETE /api/content/v1/cards/bulk
```

Body: `{ "cardIds": ["<cardId>"] }`

## File Upload in Node.js

```typescript
import { readFileSync } from 'node:fs';

const imageBuffer = readFileSync('/path/to/image.png');
const formData = new FormData();
formData.append(
  'file',
  new Blob([imageBuffer], { type: 'image/png' }),
  'image.png'
);

const res = await fetch(`${baseUrl}/api/data/v1/data-files`, {
  method: 'POST',
  headers: {
    Accept: 'application/json',
    Cookie: cookie,
    // DO NOT set Content-Type — FormData sets it automatically with the boundary
  },
  body: formData,
});
const { dataFileId } = await res.json();
```

## Verify Upload Details

After creating the card, you can verify the file was stored correctly:

```
GET /api/data/v1/data-files/{dataFileId}/details
```

**Response:**

```json
{
  "dataFileId": 61,
  "name": "image.png",
  "currentRevision": {
    "dataFileRevisionId": 62,
    "contentType": "image/png",
    "sizeBytes": 2183044,
    "scanState": "SAFE"
  }
}
```

The `scanState: "SAFE"` confirms the file passed Domo's virus/content scan.

## Gotchas

1. **`documentId: "{dataFileId}:undefined"` is correct.** Do not replace "undefined"
   with the actual revision ID. The UI literally sends "undefined" and the server
   resolves the revision internally. Using the real revision ID may cause unexpected
   behavior.

2. **Do NOT set Content-Type for the file upload.** Setting `Content-Type: multipart/form-data`
   manually omits the boundary parameter and breaks the upload. Let `FormData`/fetch
   generate it automatically.

3. **The 404 from `doc-previews/meta` is normal.** Image processing is asynchronous.
   The first few polls will 404. Wait ~2–5 seconds before the meta endpoint returns 200.
   The app will load correctly regardless — the image renders once processing completes.

4. **No rooster/query step.** Unlike Gallery, List, and Banner, Image has no data
   binding. There is no `PUT /api/content/v1/cards/rooster/query` call and no
   subscription to attach.

5. **`revisionId` is in `metadata.revisionId` (string), not the top-level response.**
   Both are present, but the doc-preview URL uses the string revision ID from
   `metadata.revisionId`.

6. **Image component is purely static.** It does not connect to a dataset, does not
   update when data changes, and does not support variable bindings. For dynamic
   images (e.g., per-row images in a list), use the `image-widget` inside a List or
   Banner component instead.

7. **Same `layoutId` gotcha as all AppStudio components.** POST dataapps with a
   minimal body returns `views[0].layout = null`. Always include `owners`, `enabled`,
   `showNavigation`, etc.

## When to Use

### Best For
- **Logos and branding** — company logo, product badge, brand header at the top of an
  app page
- **Static infographics or maps** — pre-built charts, geographic overlays, process
  diagrams, org charts that don't need to update
- **Instructional content** — how-to screenshots, training diagrams, reference images
- **Page headers / hero images** — visual framing for an AppStudio page
- **Spacers with visual weight** — when a page needs visual separation or an
  anchor point that isn't a data card

### Power Features
- **Zero configuration** — no dataset, no DML, no params. The simplest AppStudio
  component to add. Upload once, it displays forever.
- **Full-resolution rendering** — the doc-preview system generates PNG previews at
  request resolution. Large, high-quality images are supported.
- **SAFE scan on upload** — Domo scans uploaded files for malware. `scanState: "SAFE"`
  is confirmed before the image is available in the app.

### Business Domains
- **Branding / Marketing** — logo placement, campaign imagery, brand standards panels
- **Sales enablement** — product images, territory maps, reference materials
- **Operations** — process flow diagrams, org charts, facility maps
- **Training / Enablement** — annotated screenshots, step-by-step visual guides
- **Executive dashboards** — header imagery to brand the dashboard for a specific team
  or initiative

### Do NOT Use When
- The image needs to update dynamically based on data → use `image-widget` in a
  List, Banner, or Gallery rooster card instead
- You want images per row in a list → List or Banner with `image-widget` bound to
  a URL column
- The "image" is actually a chart → use a KPI or visualization card, not Image
- You need the user to upload their own image at runtime → Image is uploaded at
  app-build time, not at user runtime

### Anti-Patterns
- **Using Image for data-driven content.** The Image component is static — it
  doesn't refresh. If you upload an infographic that will need updating, you'll
  have to re-upload manually every time. For dynamic content, use a data card.
- **Uploading oversized images.** Very large images (10MB+) are slow to process
  and render. Resize images before upload — 150KB–2MB is the right range.
- **Using Image as a background fill.** AppStudio doesn't composite the Image card
  behind other cards. It's a discrete card in the layout grid. For backgrounds,
  use app theme settings instead.
- **One Image card per logo instance.** Upload the logo once, reuse the same
  `cardId` across pages. Don't re-upload the same image for every page.

### Integration Patterns
- **Logo + KPI row** — Image card (logo) beside KPI summary cards at the top of a page
- **Header image + list/gallery** — Visual hero image above a data component to brand
  the view
- **Diagram + detail panel** — A static process or architecture diagram alongside a
  table or list showing the underlying data
